I'm working in Kiro (AWS's agentic IDE) with custom skills and steering files. We have a
code-assessment pipeline (internally called "atx") that analyzes a codebase and writes its
findings as Markdown into an ATXDocumentation/ folder. From that analysis we produce two
deliverables:
  1) a Word (.docx) assessment report compiled from the analysis Markdown, and
  2) Kiro spec files (Markdown) for a modernization plan.

PROBLEM: During the DOCX step, the agent writes a brand-new python-docx generator script on
every run and then executes it to produce the report. This is slow (it's most of the run),
non-deterministic (formatting/structure drift between runs), and error-prone (each fresh
script re-introduces the same python-docx mistakes: TOC fields, heading styles/outline levels,
image embedding, captions).

CONSTRAINTS / FACTS:
- python-docx is already used elsewhere in the toolchain (image embedding, a validator), so
  staying on python-docx is preferred over adding a Node/docx-js dependency.
- Diagrams are placed by section from a manifest (diagrams.json: id, source, target_section,
  png_path, title), NOT inline in the Markdown.
- A validator checks the final DOCX for: a populated Table of Contents field, dotted-decimal
  headings (e.g. "3.1 ..."), every diagram embedded as an image (matched by SHA-256), per-
  section image-to-row parity, "Figure x.y" captions preceded by their image, and coverage of
  a fixed section tree (1.1 .. 10.4 plus Appendices A–F).
- The report has a fixed section structure; only the prose and which diagrams go where vary.

WHAT I WANT FROM YOU:
1. Recommend the best-practice architecture for generating this DOCX. Specifically compare:
   (a) the current approach (LLM writes a generator script each run),
   (b) a single fixed, version-controlled assembler script + the LLM producing the report
       content as structured data,
   (c) Pandoc (Markdown -> DOCX with a reference template),
   (d) docxtpl (Jinja over a .docx template).
   Give a clear recommendation with the tradeoffs for MY constraints above.
2. Define the data contract the LLM should emit (e.g. a report-content.json schema) so the
   assembler is deterministic and the LLM only does judgment work (organizing/writing prose),
   never code authoring.
3. Provide a working python-docx assembler skeleton that consumes that content file plus
   diagrams.json and produces a report.docx that would satisfy the validator checks listed
   above (populated TOC field, numbered headings, embedded PNGs with captions, page numbers,
   US-Letter page size).
4. Tell me how to wire this into the agent so it STOPS writing ad-hoc generator scripts —
   what to change in the skill/phase that currently does assembly, and what one-line rule to
   add to always-on steering.
5. Note anything I should keep out of scope (e.g. the Markdown spec files should just be
   written directly, not generated by a script).

Keep the reasoning tight and give me concrete code + the JSON schema, not just prose.
